# Message System API Contract

## Scope

This document captures the current message-system API contract after the new
Postman export realignment.

Source of truth:

- New Postman export attached to the API realignment request

Modules covered:

- Notifications
- Rules
- Alerts UI records, backed by notification messages
- Deprecated standalone alerts endpoint

Important model changes:

- `/api/alerts` is deprecated and appears as `alerts DEPRECATED` in the new
  Postman export.
- The frontend Alerts UI must use `/api/notificationMessages`, not
  `/api/alerts`.
- Rules own embedded alert threshold definitions in their create/update
  payloads.
- Notification messages are generated by backend/trigger flow and are list plus
  status edit only in this frontend.
- Notification message create UI is removed from scope.
- Correction Factors are unrelated to this realignment and remain unchanged.

Response shapes are still treated as open until verified against the backend.
The fields below are documented from the new Postman export and API update
notes.

## Module Purposes

### Notifications

Notifications define a named delivery configuration:

- who receives a notification
- how often it is sent
- which alert types are included

### Rules

Rules define when notification evaluation should run.

A rule now connects:

- one pollen value
- one or more generated evaluation intervals
- one or more locations
- one or more notifications
- one or more embedded alert threshold definitions
- an enabled/disabled state

Rules no longer use the old POC fields:

- `measure_id`
- `location_ids`
- top-level `start_date`
- top-level `end_date`

### Embedded Rule Alerts

Embedded alerts define threshold ranges owned by a rule. They are sent inside
rule create/update payloads as:

```json
{
  "type": "yellow",
  "min_value": 0.8,
  "max_value": 1.2
}
```

These embedded alerts replace the standalone Alerts CRUD workflow for new UI
work.

### Alerts UI / Notification Messages

The UI called Alerts now maps to notification message records from
`/api/notificationMessages`.

Notification messages represent generated alert/message records connected to a
notification, rule, and embedded alert. The frontend should list these records
and allow status changes only.

Notification messages should not have create UI in this frontend. They are
created by backend trigger flow.

For Alerts UI display, `value_creation_date` is the alert/value occurrence date.
Use it for the displayed Created field. Fall back to `creation_date` only when
`value_creation_date` is missing.

## Endpoints

The upstream API uses `{{host}}/api/*`. In the frontend, these should be
accessed through internal Next API proxy routes that forward to
`POLLEN_API_BASE`.

### Notifications

Notifications remain CRUD.

```text
GET    /api/notifications
GET    /api/notifications/:notificationId
POST   /api/notifications
PUT    /api/notifications/:notificationId
DELETE /api/notifications/:notificationId
```

### Rules

Rules remain CRUD, but their payload shape has changed.

```text
GET    /api/rules
GET    /api/rules/:ruleId
POST   /api/rules
PUT    /api/rules/:ruleId
DELETE /api/rules/:ruleId
```

### Alerts Deprecated

`/api/alerts` is deprecated in the new Postman export as `alerts DEPRECATED`.

```text
GET    /api/alerts
GET    /api/alerts/:alertId
POST   /api/alerts
PUT    /api/alerts/:alertId
DELETE /api/alerts/:alertId
```

Frontend direction:

- Do not use `/api/alerts` for new work.
- Do not build new standalone Alerts CRUD against this endpoint.
- Keep any existing implementation in place until a later cleanup/migration
  slice; do not delete it as part of this documentation realignment.

### Notification Messages

The upstream API uses camelCase in the path:

```text
GET  /api/notificationMessages
GET  /api/notificationMessages/:notificationMessageId
PUT  /api/notificationMessages/:notificationMessageId
POST /api/notificationMessages/trigger
```

Frontend route/proxy naming should use kebab-case where possible, but the proxy
must forward to the upstream `notificationMessages` path.

Frontend behavior:

- Use notification messages as the data source for the Alerts UI.
- List notification messages.
- Show details if needed.
- Allow status edit only.
- Do not provide create UI.
- Do not implement trigger UI yet.

The trigger endpoint exists, but is out of scope for the current frontend work:

```text
POST /api/notificationMessages/trigger
```

## Request Payloads

### Create Notification

Notification payloads are unchanged from the prior POC until a newer export
clarifies otherwise.

```json
{
  "name": "Notification 2",
  "recipients": ["milton.loayza@enjambre.com.bo"],
  "frequency": "immediately",
  "alert_types": ["green", "yellow", "red"]
}
```

### Update Notification

```json
{
  "id": 1,
  "name": "Notification 1 update",
  "recipients": ["milton.loayza@gamil.com.bo"],
  "frequency": "immediately",
  "alert_types": ["green"]
}
```

Open question:

- Whether the new backend still expects `id` in the update body or only in the
  path.

### Create Rule

```json
{
  "name": "Rule 4",
  "pollen": "Alnus",
  "intervals": [
    {
      "start_date": "2026-04-05 00:00:00+00",
      "end_date": "2026-04-10 23:59:59+00"
    }
  ],
  "locations": ["DEBIED"],
  "notification_ids": [1],
  "alerts": [
    {
      "type": "yellow",
      "min_value": 0.8,
      "max_value": 1.2
    }
  ],
  "description": "Description 4",
  "enabled": true
}
```

### Update Rule

```json
{
  "id": 5,
  "name": "Rule 44",
  "pollen": "Alnus",
  "intervals": [
    {
      "start_date": "2026-04-05 00:00:00+00",
      "end_date": "2026-04-10 23:59:59+00"
    }
  ],
  "locations": ["DEBIED"],
  "notification_ids": [1],
  "alerts": [
    {
      "type": "red",
      "min_value": 1.2,
      "max_value": 2.0
    }
  ],
  "description": "Description 44",
  "enabled": true
}
```

Rule payload notes:

- `pollen` should be selected from `GET /api/pollen`.
- `locations` should be selected from `GET /api/locations`.
- `notification_ids` should be selected from Notifications.
- `alerts` are embedded threshold definitions managed inside the Rules form.
- `intervals` are generated by the frontend from the user-selected pollen
  flight period.

### Update Notification Message Status

Only `status` is editable through the frontend.

```json
{
  "status": "RESOLVED"
}
```

Do not send editable payloads for notification message fields such as
`notification_id`, `rule_id`, `alert_id`, `creation_date`,
`value_creation_date`, `pollen`, `location`, `value`, or `description`.

## Known Fields

### Shared

- `id`: numeric identifier in known examples. UI-normalized records may use
  string ids to match existing frontend patterns.
- `name`: display name where present.

### Notification

- `id`: notification id.
- `name`: notification name.
- `recipients`: array of email strings.
- `frequency`: delivery frequency string.
- `alert_types`: array of alert type strings.

### Rule

- `id`: rule id.
- `name`: rule name.
- `pollen`: pollen name/code selected from `/api/pollen`.
- `intervals`: array of `{ start_date, end_date }` objects generated from the
  pollen flight period.
- `locations`: array of location strings selected from `/api/locations`.
- `notification_ids`: numeric notification ids.
- `alerts`: array of embedded `{ type, min_value, max_value }` thresholds.
- `description`: free-text rule description.
- `enabled`: boolean rule state.

### Embedded Alert

- `type`: alert type string.
- `min_value`: numeric lower threshold.
- `max_value`: numeric upper threshold.

### Notification Message

- `id`: notification message id.
- `notification_id`: related notification id.
- `rule_id`: related rule id.
- `alert_id`: related embedded/backend alert id.
- `creation_date`: backend datetime string.
- `value_creation_date`: value/measurement occurrence datetime string used by
  the Alerts UI Created field, with `creation_date` as defensive fallback.
- `pollen`: pollen name/code.
- `location`: location string.
- `value`: numeric measured or reported value.
- `description`: free-text generated message description.
- `status`: message status, editable by the frontend.
- `notification`: related notification object or array of notification objects.
  Normalize defensively because older examples used one object and newer API
  responses can include multiple notifications.
- `rule`: related rule object.
- `alert`: related alert object.

Chart alignment:

- If an Alerts chart needs the alert/value occurrence date for its measurements
  window, marker, or alert context query params, prefer `value_creation_date`.
- Fall back to `creation_date` only when `value_creation_date` is missing.
- Do not otherwise change chart range, marker style, tooltip content, or
  correction-factor CTA behavior as part of date alignment.

## Dependencies Between Modules

```text
Notifications
  -> used by Rules through notification_ids
  -> referenced by Notification Messages through notification_id/notification

Rules
  -> use Pollen through pollen
  -> use Locations through locations
  -> use Notifications through notification_ids
  -> own embedded alerts through alerts
  -> referenced by Notification Messages through rule_id/rule

Notification Messages
  -> power the Alerts UI
  -> reference Notifications, Rules, and Alerts
  -> allow status updates only

Deprecated /api/alerts
  -> not used for new frontend work
```

Implementation order should respect these dependencies:

1. Notifications realignment check
2. Rules payload and form realignment
3. Alerts UI remap to notification messages
4. Removal of notification message create/edit/delete UI affordances

Correction Factors should not be changed as part of this work.

## Pollen Flight Period And Rule Intervals

For this version, the user sets the pollen flight period in the Rules UI. The
frontend generates `intervals` from that period before sending create/update
payloads.

Recommended simple v1 behavior:

- User selects a target year, flight start date, and flight end date.
- UI validates that both dates are present and in the same target year.
- UI sends one generated interval matching the selected flight period:
  `{ start_date: flightStart, end_date: flightEnd }`.
- If product/backend confirms that "remaining evaluation intervals for the
  year around that period" means before/after or rolling windows, expand the
  generator in a later slice without changing the stored form concept.

Assumptions:

- The backend accepts one or more intervals.
- A single flight-period interval is acceptable for the simple POC.
- Dates are converted to the backend datetime format already used elsewhere in
  the app.
- If the selected range crosses a year boundary, the UI should block submission
  for v1 and show a clear validation error.

Open questions:

- Should generated intervals cover only the flight period or also pre-flight
  and post-flight portions of the year?
- If multiple intervals are required, what granularity should be generated:
  daily, weekly, monthly, custom windows, or before/during/after?
- Should leap years, timezone offsets, and inclusive end-of-day handling be
  normalized by frontend or backend?
- Does the backend expect ISO timestamps, `YYYY-MM-DD`, or the
  `YYYY-MM-DD HH:mm:ss+00` style shown in older examples?

## POC Assumptions

- List endpoints return arrays or response envelopes that can be normalized to
  arrays.
- Detail endpoints return a single record or response envelope that can be
  normalized to one record.
- Create/update rule endpoints accept the new embedded-alert request shape.
- Notification message status update uses only `{ "status": "RESOLVED" }`.
- Delete endpoints for notifications and rules should be treated as successful
  on any `2xx` response, even if the response body is empty.
- No query parameters are documented for message-system list endpoints.
- No final Figma design or final workflow design is part of this POC
  realignment.
- No shared CRUD framework should be introduced for this work.
- All user-facing frontend text must use `next-intl` when implementation
  begins.

## Open Questions

- What are the exact response shapes for notifications, rules, and notification
  messages?
- Are ids always numbers, or can the backend return strings?
- Which notification `frequency` values are valid?
- What is the full valid set of embedded alert `type` values?
- What is the full valid set of notification message `status` values?
- What exact value from `/api/pollen` should be sent as rule `pollen`?
- What exact value from `/api/locations` should be sent in rule `locations`?
- Should rule update payloads include `id`, or should the path id be the only
  id?
- Are embedded alert ids returned on rule detail, and if so should update
  preserve them or resend thresholds without ids?
- What interval-generation algorithm does the backend/product expect beyond
  the simple flight-period interval?
- Are there server-side constraints for overlapping rules, overlapping
  intervals, alert value ranges, or duplicate notification recipients?
