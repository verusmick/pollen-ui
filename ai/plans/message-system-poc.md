## Direction Changes

The previous POC implemented:

- Notifications CRUD
- Rules CRUD with old `measure_id`, `start_date`, `end_date`, and
  `location_ids` fields
- Alerts CRUD backed by `/api/alerts`
- Notification messages CRUD under
  `/rules-and-notifications/notification-messages`

The new model changes that direction:

- `/api/alerts` is deprecated and should not be used for new frontend work.
- Rules own embedded alert thresholds in their create/update payloads.
- The UI called Alerts is backed by `/api/notificationMessages`.
- Notification messages are generated by backend/trigger flow.
- Notification messages are list plus status edit only.
- Notification message create UI is removed from scope.
- The trigger endpoint exists but should not get UI yet.
- Correction Factors remain unchanged.

## Types And Payload Mapping

Keep API payload types and UI-normalized record types in route-local
`types/messageSystem.ts` unless a small API helper type belongs in
`src/lib/api/messageSystem.ts`.

Recommended normalization:

- API ids can be `string | number`.
- UI ids should be strings.
- arrays should default to `[]` in mappers.
- missing optional text should default to `''` in form values.
- response envelopes should be normalized defensively once verified.

### Rule Types

Rules should use the new payload fields:

```ts
type RulePayload = {
  name: string;
  pollen: string;
  intervals: Array<{
    start_date: string;
    end_date: string;
  }>;
  locations: string[];
  notification_ids: number[];
  alerts: Array<{
    type: string;

    max_value: number;
```

Remove old POC fields from new rule form values and payload builders:

- `location_ids`

## Pollen Flight Period And Interval Generation

The Rules UI should stay simple while preparing the correct payload.

Recommended simple v1:

- User selects pollen, locations, notifications, embedded alerts, and a pollen
  flight period.
- The flight period is captured as start and end month/day values.
- The frontend validates that the end date is not before the start date.
- The frontend generates one interval matching the chosen flight period with
  fixed year 2000, because the API ignores the year and this supports Feb 29.
- The generated interval is sent as:

```json
{
  "intervals": [
    {
      "start_date": "2000-04-05 00:00:00+00",
      "end_date": "2000-04-10 23:59:59+00"
    }
  ]
}
```

This supersedes the earlier outside-period interval assumption for the active
Rules form.

Potential later expansions:

- split the flight period into weekly or monthly intervals
- generate rolling evaluation windows
- allow year-crossing flight periods

Edge cases to handle or explicitly block in v1:

- missing start or end date
- end date before start date
- date range crossing a year boundary
- timezone conversion around local midnight
- duplicate or empty generated intervals

## Risks And Open Questions

Risks:

- Existing implemented screens still follow the old contract until future code
  slices realign them.
- Response shapes are unknown because the Postman export details available here
  focus on request fields and paths.
- `/api/alerts` may still be referenced by existing frontend code and should be
  migrated carefully before deletion.
- Rule detail responses may include embedded alert ids or nested shapes that
  require mapper changes.
- Notification message status values are not fully known.
- Pollen and location endpoint response shapes need verification.
- Date formatting for generated intervals may need backend-specific conversion.

Open questions:

- What exact field from `/api/pollen` should become rule `pollen`?
- What exact field from `/api/locations` should become each rule `locations`
  entry?
- What is the full status enum for notification messages?
- What is the full alert type enum for embedded rule alerts?
- Should rule update preserve embedded alert ids if the backend returns them?
- What interval-generation algorithm is expected for "remaining evaluation
  intervals for the year around" the pollen flight period?
- Should generated intervals include only the flight period for v1, or also
  before/after windows?
- Does the trigger endpoint require a body, and what side effects should the UI
  eventually communicate if it is later exposed?
